Phase 2 supports per-user launchd on macOS and systemd --user on Linux. There is no published npm release; build from source. Do not claim clean-machine onboarding or broad model qualification is complete.

Check `spillway --version`, `spillway service status` and queue_status. After the service starts, run `spillway doctor` (or `--json`) for bounded operational diagnostics. It checks local catalog/harness and execution/evidence health without inference, installing software, changing policy or certifying model capability. A failure needs resolution; warnings describe busy work, skipped nonlocal catalogs or operator-asserted qualifications. Use `spillway pilot create NEW_DIRECTORY` outside existing Git checkouts to prepare versioned tasks and protected fixtures, without banking or acceptance. Source setup uses Node >=22.13, npm ci, npm run check, and optional npm link, which changes local npm executable links. Honor existing human authorization for these reversible local setup steps and service installation; do not ask repeatedly. Obtain authorization only for a new action outside the request, such as credentials, provider enrollment or infrastructure.

For new configuration, copy examples/init-input.example.json into a private owner-only file/directory outside Git, fill explicit repo/local endpoint/model/artifact/harness bindings, and use `spillway init --from INPUT --directory NEW_ROOT`. It creates only a new private config.yaml/data and returns their paths; no probing, service start, class grants or replacement. The parent must exist and be owned/canonical/not writable by others. Use the returned --config path for service/queue commands. Empty qualified_classes permits startup diagnostics/explicit qualification; ordinary local tasks remain disabled until the owner explicitly asserts tested classes. Do not fill grants from fixtures or tool-workload qualification. Existing private configs remain supported; use registered repositories and explicit data policy. Private config/data stay outside all Git repositories. After validating config and stopping an existing foreground service, run `spillway --config ABSOLUTE_CONFIG_PATH service install` to install/start under the current user. `--no-start` renders/writes the private service definition without starting it. Use service start/stop/status/uninstall for lifecycle; uninstall retains config, queue and evidence. Reinstall after moving/upgrading the pinned Node or built CLI path. Linux uses the logged-in user manager; lingering/login persistence is an owner OS decision and is not enabled by Spillway.

Daemon environment contains PATH only, with manager-inherited provider keys removed. For an authenticated configured endpoint, use the private api_key_file reference documented in the README; never copy keys into plist/unit files or enroll frontier credentials. Foreground api_key_env remains available where explicitly configured. Exact harness version and profile qualification remain operator assertions requiring real endpoint testing. Default local review now runs on the approved local/review profile; frontier work runs only in explicitly authorized Claude Code sessions. Do not launch paid providers, provision infrastructure, enable frontier, change repository approval or invent model qualification during setup.
